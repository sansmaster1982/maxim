# Разбор протокола MAX

Заметки по сетевому протоколу мессенджера MAX (`api.oneme.ru`), полученные
анализом трафика и поведения клиента. Здесь — только описание интерфейса
(формат кадра, опкоды, последовательности), нужное для совместимого клиента.
Исходников официального приложения тут нет и не будет: это разбор протокола, а
не копия чужого кода. Полная рабочая спецификация — в [PROTOCOL.md](PROTOCOL.md);
этот файл — про то, что и как удалось восстановить.

## Транспорт и кадр

- Транспорт: TLS на `api.oneme.ru:443`. Снаружи неотличимо от обычного HTTPS,
  поэтому DPI его не выделяет.
- Сообщение — бинарный кадр: 10-байтный заголовок + тело. Тело — msgpack,
  поверх которого может лежать сжатие.
- Сжатие тела определяется по старшему байту поля длины (`cof`): основной поток
  идёт LZ4-фреймом, изредка встречается zstd без словаря. LZ4-распаковка
  реализована на чистом Dart, чтобы не тащить нативную зависимость.
- Каждый запрос несёт seq; ответ приходит с тем же seq и полем `cmd`
  (1 — успех, 3 — отказ с человекочитаемой причиной в payload).

## Карта опкодов

Операции — это числовые опкоды. Те, что подтверждены и используются:

| Опкод | Назначение |
| --- | --- |
| 6 | INIT — рукопожатие, userAgent устройства + deviceId |
| 16 | PROFILE — чтение профиля; та же команда пишет своё имя (firstName/lastName) |
| 17 | AUTH_REQUEST — запрос SMS-кода (`type=START_AUTH`) |
| 18 / 23 | AUTH_CONFIRM — подтверждение кода (вход или регистрация, см. ниже) |
| 19 | LOGIN — вход по токену, отдаёт снапшот чатов/профиля |
| 32 | CONTACT_INFO — профили контактов по списку id |
| 34 | CONTACT_UPDATE — кастомное имя для контакта (как ты его назвал) |
| 46 | поиск контакта по номеру (поведенческий бан-сигнал, троттлить) |
| 48 | CHAT_INFO — данные чата |
| 49 | история сообщений (пагинация) |
| 51 | медиа-галерея чата |
| 64 | MSG_SEND — отправка сообщения |
| 65 | индикатор «печатает» |
| 67 | MSG_EDIT — редактирование |
| 80 | загрузка фото (двухступенчатая) |
| 96 / 97 | список активных сессий / завершение чужой сессии |
| 115 | TWO_FA — проверка пароля второго фактора |
| 128 | входящий push (новые сообщения и события) |
| 142 | удаление сообщения |
| 155 / 156 | push обновления реакций |
| 178 / 179 | поставить / снять реакцию |
| 199 / 200 | удаление профиля / по времени |
| 202 | транскрипция голосового/видео-сообщения |

## Авторизация: вход и регистрация — один флоу

Последовательность SMS-входа:

1. `op17` AUTH_REQUEST → `{phone, type:"START_AUTH"}`. В ответ — короткоживущий
   токен запроса.
2. `op18` (вариант `op23`) AUTH_CONFIRM → подтверждение кода.
3. `op19` LOGIN с полученным auth-токеном → сессия.
4. Если у аккаунта включён второй фактор — между шагами 2 и 3 идёт `op115`
   с `{trackId, password}`, и уже его результат уходит в LOGIN.

Ключевая находка: **регистрация нового аккаунта — это не отдельный опкод**, а тот
же AUTH_CONFIRM, отличающийся одним полем `tokenType`. При входе клиент шлёт
`CHECK_CODE`; при регистрации — `REGISTER` плюс обязательное `firstName`
(опционально lastName и аватар). Сервер по этому полю решает, войти в
существующий аккаунт или завести новый.

В протоколе авторизации **нет** ни капчи, ни согласия с условиями, ни
device-attestation (Play Integrity / SafetyNet / DeviceCheck). Идентификатор
устройства — самопровозглашённые `userAgent` + `deviceId` в INIT, которые
клиент задаёт сам. То есть технического барьера для регистрации сторонним
клиентом нет; ограничение — поведенческое (см. анти-фрод).

## Токены привязаны к типу устройства

- WEB-токен (из веб-версии) принимается только при `deviceType=WEB`.
- ANDROID-токен (вход по SMS) — при `deviceType=ANDROID`.
- Под VPN с локацией вне страны регистрации сервер выключает phone-auth
  (`phone-auth-enabled:false`).

## Медиа

Отправка вложения — двухступенчатая: сперва запрос на загрузку (получаем
upload-URL и токен), затем заливка байтов на CDN (`i.oneme.ru`), затем отправка
сообщения (`op64`) со ссылкой на загруженное. Скачивание — по `baseUrl` с
токеном в адресе.

## Анти-фрод и устойчивость

Эмпирические находки, не из документации сервера:

- Баны идут по **номеру / IP / поведению**, а не по анализу клиента. Подделка
  TLS или маскировка «не мод» не помогает.
- Главный технический бан-сигнал самописного клиента — **шторм сессий**: без
  keepalive сервер роняет идущий сокет, наивный реконнект делает INIT+LOGIN
  каждые ~30 секунд, и антифрод видит десятки созданий сессии на одном номере.
- Лечение: keepalive `op16` (PROFILE с пустым payload) каждые 25 секунд держит
  сокет; политика реконнекта с полом 1 LOGIN / 30 секунд, backoff и брейкером
  гасит шторм. Стабильный `deviceId` на всю установку убирает сигнал «новое
  устройство на каждый запуск».
- Свежая SIM и репутация номера клиентом не лечатся — это серверная история.
  Поэтому вход в уже живой аккаунт безопаснее регистрации свежего.

## Чем это не является

Это описание сетевого интерфейса для совместимого клиента — формат кадра,
номера опкодов, последовательности. Здесь нет исходного кода официального
приложения и его декомпила. Цель — задокументировать протокол, чтобы по нему
можно было написать свой клиент, а не воспроизвести чужой продукт.
